## R1 — HIGH: request-template extraction loses auth failure classification

Trigger: a request template contains forbidden inline `auth`, including a template that
also declares `authRef`. The template must remain rejected.

Before B02, TemplateLoader.validateAuthShape raised
AuthFailureException.configuration, preserved in the loader exception chain. Now
RequestTemplateParser.authProblems records INLINE_AUTH and parse throws a generic
RequestTemplateException; request-template-files/TemplateLoader.parseFile wraps it in
IllegalStateException. No AuthFailureException survives.

Both real consumers still use AuthFailureException.find to select auth handling:

- request-builder-service/RequestBuilderWorkerImpl.java:200–234;
- http-sequence-service/HttpSequenceRunner.java:161–177.

Their auth path records AuthFailureJournalDeduplicator and emits the first failure;
repeated occurrences return null. The changed exception bypasses that path and takes
the generic runtime-failure branch on every affected invocation. This changes error
classification and repeated-alert behavior while still rejecting the same input.

Changed locations:

- `common/request-templates/src/main/java/io/pockethive/requesttemplates/RequestTemplateParser.java:40–42,68–70`;
- `common/request-template-files/src/main/java/io/pockethive/requesttemplates/files/TemplateLoader.java:70–74`.

Correction: preserve the auth failure category through the runtime boundary using the
canonical auth failure contract. Keep decoded template validation in RequestTemplateParser;
do not recreate inline-auth validation in each worker. Cover the observable classification
and repeated-failure behavior, rather than merely asserting an exception message.
