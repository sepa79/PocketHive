# Use optional Redis dataset hand-offs

| Reader context | Details |
| --- | --- |
| Audience | Scenario authors evaluating Redis-backed state hand-offs |
| Prerequisites | Understand scenario bundles and swarms; use Redis only when the scenario explicitly requires shared dataset state |
| Expected outcome | Choose between a one-swarm loop and a multi-swarm hand-off without treating either pattern as required architecture |
| Last verified PocketHive version | PocketHive `v0.15.35` |

This is a worked example, not a required PocketHive architecture. Use it when a
scenario needs durable, observable hand-off states backed by Redis lists.

## One-swarm loop

A worker can read a record from `Ready`, perform an authorization-like
operation, and move it to `TopUpNeeded` when follow-up work is required. A
later operation returns the record to `Ready`.

## Multi-swarm hand-off

Two swarms can cooperate through the same named dataset states:

- Swarm A reads from `Ready` and writes to `TopUpNeeded`.
- Swarm B waits on `TopUpNeeded`, performs its operation, and writes back to
  `Ready`.

Each swarm still has its own control plane and lifecycle. Redis provides the
work-data hand-off between them.

## Troubleshooting

Confirm the scenario declares the intended Redis dataset names and that each
swarm is healthy before inspecting Redis directly. Use the
[operator troubleshooting workflow](../operators/observability-troubleshooting.md)
and treat Redis Commander as a focused diagnostic surface, not the source of
swarm lifecycle truth.
